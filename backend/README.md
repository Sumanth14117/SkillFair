# SkillFair Skills Discovery API

Python 3.14.7 is the tested development version for the pinned dependency lock. The runtime dependency ranges support Python 3.11+, but the lock should be regenerated and validated before using another interpreter. From this directory, create and activate a virtual environment. `requirements.txt` contains runtime dependencies only; `requirements-dev.txt` adds test dependencies. Install the pinned development/test environment from `requirements-lock.txt` for a reproducible local test setup:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-lock.txt
.\run-local.ps1
```

The local launcher uses the absolute `backend/.env` path, starts from the backend directory, and clears an inherited `SKILLFAIR_AUTH_ALLOWED_ORIGINS` so Uvicorn loads the configured exact origins from that file. It is for local development only; production must set its own exact HTTPS origins and must not use this launcher.

## PostgreSQL persistence schema

The repository includes a lazy SQLAlchemy 2.x engine/session foundation, PostgreSQL `psycopg` driver, ORM metadata in `app/db_models.py`, and Alembic configuration under `alembic.ini` and `migrations/`. Revision `202610310001` has been applied to the local SkillFair database. Installing dependencies or starting the API does not create or modify tables. Registered account-owned HTTP routes use PostgreSQL persistence; in-memory stores retained in the domain layer support isolated unit-test adapters and are not the source of truth for registered persistence routes.

`DATABASE_URL` is optional for public health and provider-status checks. Authenticated Skills Discovery, analysis lookup, matching against saved evidence, and Career Orchestrator persistence require a reachable database and return a controlled service-unavailable response when it is unavailable. `GET /api/health/database` performs a one-shot `SELECT 1` and returns only configured/reachable status, never connection details. PostgreSQL URLs using `postgresql://` are normalized to the installed psycopg 3 driver. SQLite URLs are supported for isolated tests only; SQLite test results do not demonstrate PostgreSQL compatibility.

Add a local `DATABASE_URL` to `backend/.env` or supply it through the deployment secret/configuration mechanism. Do not commit credentials. A placeholder is provided in `.env.example`. The engine is created lazily, uses connection pre-ping and a bounded pool (5 pooled connections, 5 overflow, 10-second pool wait), and is disposed during application shutdown. FastAPI's `get_db_session` dependency rolls back on exceptions and always closes the session. ORM definitions include ownership-scoped foreign keys and only redacted skill evidence; they have no columns for uploaded files, full resume text, raw session tokens, review notes, or free-text feedback.

The initial revision is `migrations/versions/202610310001_initial_schema.py`. Alembic loads `backend/.env` without printing its values and uses `SKILLFAIR_MIGRATION_DATABASE_URL` only; it never falls back to the runtime `DATABASE_URL`. Configure the runtime URL with the restricted application role and the migration URL with the schema-owner role. Keep both URLs private and do not commit `.env`. Review migrations before use; `python -m alembic history` is read-only, while `python -m alembic upgrade head` changes the selected database and requires explicit approval and target verification. Never point test or review commands at production data.

## Backend authentication foundation

The backend provides `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, and `GET /api/auth/me`. Registration validates and case-normalizes email addresses, requires a 12–128 character password, and stores only an Argon2id hash. New and already-registered addresses receive the same HTTP 202 response and body, with no session cookie; users sign in explicitly afterward. No verification email is sent. This reduces direct registration enumeration but cannot prevent a user from testing login credentials they already know. Login uses a generic failure response for unknown, inactive, or incorrect accounts and rotates any existing session identifier. The current-user endpoint returns only the account ID, normalized email, and creation timestamp.

Sessions use a cryptographically random opaque `skillfair_session` cookie. PostgreSQL stores only its SHA-256 digest, plus a digest of the CSRF token. The session cookie is HTTP-only, SameSite=Lax, and Secure by default; set `SKILLFAIR_AUTH_COOKIE_SECURE=false` only for local HTTP development and require `true` behind HTTPS in deployed environments. Sessions expire after 30 minutes idle or 12 hours absolute, whichever comes first. Logout revokes the server-side session.

State-changing authentication requests require an allowed Origin (or matching Referer). Logout additionally requires the readable `skillfair_csrf` cookie value in the `X-CSRF-Token` header, validated against the stored session digest. Configure `SKILLFAIR_AUTH_ALLOWED_ORIGINS` as a comma-separated exact origin list; it must remain aligned with the application's CORS policy. Local development defaults permit only `http://localhost` and `http://127.0.0.1` on Vite ports 5173 and 5174. If this variable is explicitly set in `backend/.env`, add the actual Vite origin to that exact list; configured values replace the defaults. Production deployments should set only their exact HTTPS frontend origins. Authentication routes have a separate in-memory rate limit of 10 requests per minute per client; forwarded IP headers are not trusted, and this limiter is process-local.

The authenticated frontend stores only navigation and draft convenience state in sessionStorage. On sign-in or refresh it restores the latest analysis and workflow from owner-scoped database endpoints; browser-stored IDs are not trusted as proof of ownership. Skills Discovery, matching with candidate evidence, Learning Pathways, Transferable Skills, and Career Orchestrator analysis/workflow routes require the authenticated user. Skills Discovery, workflow creation, review decisions, and review-start recording also require Origin/Referer and CSRF checks.

Validated skill records and redacted evidence excerpts are stored in `resume_analyses` and `analysis_skills`; original files and complete extracted resume text are not persisted. Career Orchestrator request fields and typed response snapshots are stored in `career_workflows`; decision, reviewed requirement IDs, owning account, and start/completion timestamps are stored in `workflow_reviews`. The existing schema intentionally does not persist free-text review notes. Workflow history has no automatic expiry or deletion workflow. Impact Measurement uses the same authenticated account boundary; recruiter feedback and baseline observations are stored in existing tables, while review metrics derive directly from `workflow_reviews` and `career_workflows`.

Database workflows use row-level locks for review transitions so competing workers cannot both commit conflicting decisions. Identical decisions with the same reviewed requirement identifiers are idempotent; a conflicting second decision returns 409. The reviewer is associated with the authenticated account, but there is no independent identity verification or immutable production audit trail.

For local cookie behavior over plain HTTP, configure the Secure flag for local development and use the same-origin Vite `/api` proxy. Do not disable Secure in HTTPS deployments. Install the Argon2 implementation with `python -m pip install -r requirements.txt`; run authentication tests with `python -m pytest -q tests/test_auth.py` and persistence tests with `python -m pytest -q tests/test_persistent_account_data.py`.

The `--env-file .env` option is required for Uvicorn to load this directory's `.env`; the application does not load `.env` files by itself. If no provider is configured, Skills Discovery defaults to local deterministic analysis. An explicit AI request returns a controlled unavailable response rather than falling back to local mode.

The API listens at `http://127.0.0.1:8000`; health check: `GET /api/health`. The Vite development server proxies `/api` to this service. Upload a PDF or DOCX (up to 10 MB) from the Skills Discovery page. Uploaded files are not intentionally retained as permanent application files. Starlette's multipart parser uses `SpooledTemporaryFile` with an approximately 1 MiB in-memory threshold; larger uploads may temporarily spill to the operating system's temporary directory. The endpoint closes the upload file in a `finally` cleanup path on normal completion and endpoint-side failures; Starlette handles cleanup for multipart parsing failures. Deployment operators should use an appropriately permission-restricted temporary directory and review its cleanup and storage policies. The application does not claim temporary storage is encrypted. PDF parsing is limited to 100 pages by default; configure `SKILLFAIR_MAX_PDF_PAGES` from 1 to 500 to change that limit. DOCX parsing is bounded to 50 MiB expanded archive size, 1,000 entries, a 100:1 per-entry compression ratio, 20 MiB combined XML, 10 MiB per XML part, 200,000 XML elements and XML nesting depth 64. A request-body middleware rejects requests above `SKILLFAIR_MAX_REQUEST_BODY_BYTES` (12 MiB by default, configurable up to 60 MiB) before FastAPI's multipart parsing when `Content-Length` is available, and counts streamed `http.request` chunks otherwise. It also drains and counts any unread request-body remainder before forwarding response headers, so body-ignoring routes cannot return success for an oversized streamed body. The middleware discards drained bytes rather than buffering them; it stops draining on ASGI `http.disconnect` and does not leave a background body-consumer task running. Since ASGI receive waits for body completion or disconnect, deploy behind a server or reverse proxy configured with request-body read/idle timeouts and a request-body cap; the application middleware does not impose a total request duration. Configure the body cap above the upload-file limit to allow for multipart framing. The endpoint still independently enforces `SKILLFAIR_MAX_UPLOAD_BYTES` (10 MiB by default). These application controls do not replace edge protections against slow or oversized network traffic.

All `/api/` operations except health and CORS preflight are rate limited by the ASGI client's peer IP; forwarded IP headers are ignored. Defaults per 60-second fixed window are 5 requests for Skills Discovery, 20 for Career Orchestrator routes, and 60 for other API routes. Configure these with `SKILLFAIR_DISCOVERY_RATE_LIMIT_PER_MINUTE`, `SKILLFAIR_ORCHESTRATOR_RATE_LIMIT_PER_MINUTE`, and `SKILLFAIR_RATE_LIMIT_PER_MINUTE` respectively (each 1–10,000). Rejected requests return 429 with `Retry-After`. The in-memory tracker is thread-safe and capped at 10,000 client/route buckets; when full, it rejects new client buckets until entries expire rather than evicting active limits. It is process-local, resets on restart, and does not coordinate across workers or instances. Behind a reverse proxy, requests may share the proxy peer IP because forwarded headers are intentionally not trusted; configure a trusted-proxy-aware edge limiter for production.

Successful authenticated Skills Discovery responses include an opaque `analysis_id`. The backend persists the analysis and validated, redacted skill evidence in `resume_analyses` and `analysis_skills`; `GET /api/skills/analyses/latest` returns the signed-in account's latest analysis for recovery. Matching, Inclusive Matching, Learning Pathways, Transferable Skills, and Career Orchestrator resolve candidate evidence using both the public analysis ID and authenticated owner ID. Client-supplied skill records and excerpts are never accepted. Resume files and complete extracted resume text are not persisted. IDs are locators, not authentication; owner-scoped queries and the authenticated session provide access control.

Before skill evidence excerpts and relevance explanations are returned or stored in provenance, the backend conservatively masks recognizable email addresses, common North American phone numbers, plus-prefixed international phone numbers, and URLs that visibly contain those values or use contact-identifying query parameters (such as `email`, `phone`, or `username`). AI-generated skill labels containing recognizable contact values or any URL are rejected rather than rewritten as skills; ordinary technical labels are preserved. Section attribution and evidence classifications are unchanged. This is PII minimization, not complete detection: personal names, postal addresses, indirect identifiers, unusual phone formats, and personal identifiers embedded in ordinary URL paths may not be recognized. Full extracted resume text is not returned in Skills Discovery responses and is not stored in the provenance store. It is transiently handled during request processing and may be sent to the configured Google Gemini or Groq provider only when that request includes explicit consent. Multipart uploads may temporarily spool to operating-system temporary storage as described above.

`POST /api/learning/pathways` accepts `job_title`, `required_skills`, and an optional `analysis_id`. The registered authenticated HTTP route resolves an optional analysis using both its public identifier and the signed-in account ID from PostgreSQL. Without an analysis ID, each requirement is marked `not_compared` and receives general activities. Responses distinguish `explicitly_evidenced`, `inferred_unverified`, `not_evidenced_in_analysis`, and `not_compared`; missing evidence is not treated as proof that someone lacks a skill. Suggested activities are deterministic practice, project, and demonstration prompts, not courses or credentials. They do not claim training completion, rank candidates, or make hiring decisions.

`POST /api/skills/transferability` accepts `source_role`, `target_role`, optional `analysis_id`, and optional `target_requirements`. The registered authenticated HTTP route resolves optional validated evidence from PostgreSQL using both the analysis identifier and signed-in account ID; clients cannot submit skills or excerpts. It reports exact normalized name matches separately from potential relationships in a small directional rule set (SQL to data reporting, for example). Such relationships are adjacent capability signals, not equivalencies or proof of qualification. Without an analysis ID, requirements are marked `not_compared` and the response offers generic prompts without candidate-specific claims. Source-role titles are user-provided context; stored evidence is not independently associated with a particular past role.

The Career Orchestrator uses `POST /api/career/orchestrator/runs` with `analysis_id`, `job_title`, `job_description`, optional `geography`, and essential/preferred skill lists. It resolves validated evidence from the authenticated owner's saved analysis, returns a minimal Skill Passport summary without extracted resume text, queries the existing market-data service, runs Job Audit once, and reuses those findings in Inclusive Matching. Missing market data is represented as `unavailable`; provider failure is a stage error and does not discard other results. The workflow is returned with human review pending and Learning Pathways blocked. `GET /api/career/orchestrator/runs?limit=20` lists up to 20 unexpired workflows owned by the signed-in account, ordered by persisted creation time newest first, and includes persisted creation and update timestamps plus status. Career Orchestrator's Recent Workflows section reopens a selected item by its exact `run_id` via `GET /api/career/orchestrator/runs/{run_id}`; it never falls back to another or latest workflow. The list remains account-scoped and requires authentication. The Recruiter Review frontend presents the current workflow and is not a multi-candidate queue.

After reviewing every returned `req-NNN` identifier, the authenticated owner may call `POST /api/career/orchestrator/runs/{run_id}/review` with `decision` set to `proceed`, `revise`, or `stop`, and the reviewed identifiers. CSRF and exact-origin checks apply. Review decisions and timestamps are stored in `workflow_reviews`; state transitions lock the workflow row and commit atomically across workers. Identical decision/requirement submissions are idempotent; conflicting subsequent decisions return 409. Learning Pathways are generated only for `proceed`. `revise` leaves pathways blocked and requires starting a new run with revised inputs; `stop` does not generate pathways. The review is attributed to the authenticated account, but that account does not independently verify a person's identity. Free-text review notes are not persisted. Workflow data survives backend restarts and is shared across workers. Analysis and workflow rows currently have no automatic expiry; account-data deletion and retention controls are future work. The orchestrator does not rank or reject candidates, infer demographics, establish competence, or prove fairness or legal compliance.

`POST /api/market/intelligence` accepts `{ "job_title": "Data Engineer", "geography": "Toronto, CA" }`; geography is optional. The response echoes the requested role and geography and includes `data_availability`, `sources`, `insights`, and a message. With the current default configuration, no provider is registered, so the endpoint deterministically returns `data_availability: "unavailable"`, empty source and insight lists, and an explanation. It makes no external requests and does not return sample statistics.

Future market-data integrations sit behind `MarketDataProvider` in `app/market_intelligence.py`. A provider must return typed insights that reference a source record marked verified, with a source identifier, name, type, source reference, and timezone-aware retrieval timestamp; publication date and geography are included when supplied by the source. The endpoint rejects unverified or unattributed data. A future SAP adapter can implement this boundary and map the customer's approved SAP market/talent data into these models without changing the public response contract. No SAP service is currently configured or connected.

Market Intelligence is limited to data returned by a configured, verified provider. It does not estimate demand, job counts, compensation, or employer activity, and it does not make matching or hiring decisions. Source coverage, freshness, and geographic scope will depend on the provider and must be displayed and reviewed with each insight.

## Impact Measurement (authenticated prototype)

Impact Measurement is scoped to the signed-in account. `GET /api/impact/summary` requires a valid session and returns only aggregates for that account. Optional `start_date` and `end_date` use inclusive UTC calendar dates; `category` may be `all`, `operations`, `recruiter_feedback`, `candidate_feedback`, or `baseline`. No endpoint returns individual measurement records, account IDs, submission IDs, or workflow IDs.

- Review starts are recorded in `workflow_reviews.review_started_at`; committed Proceed/Revise/Stop decisions and completion timestamps are read from the same workflow review row. The summary joins owner-scoped `workflow_reviews` and `career_workflows`; it does not create duplicate `impact_observations` for review activity.
- A Learning Pathways outcome counts only for a committed Proceed where the persisted workflow status is complete and the stored typed pathway stage contains a valid completed result.
- `POST /api/impact/feedback/recruiter` requires authentication, Origin/Referer and CSRF validation. It accepts an idempotency `submission_id`, `consent_to_aggregate: true`, and `evidence_usefulness`, `explanation_clarity`, and `review_ease` ratings from 1 to 5. An optional `workflow_id` is checked against the authenticated owner's active workflows. The authenticated owner is set by the backend, never the request.
- `POST /api/impact/baseline-observations` requires authentication and CSRF validation. It accepts an idempotency `submission_id`, consent, and `review_duration_seconds` from 1 to 14,400. The backend associates it with the signed-in account. Baselines are manually entered and not independently verified.
- `POST /api/impact/feedback/candidate` is retained as a compatibility route but returns HTTP 410 after authentication and CSRF checks. Candidate feedback is not stored or counted until a separate candidate identity or reviewed anonymous-submission design exists; it is never attributed to a recruiter.

Recruiter feedback and baseline rows are marked for reporting for up to 90 days. Expired rows are excluded and pruned on that account's next Impact API access; a dormant account's expired rows can remain stored until the next access. The pruning query is owner-scoped and deletes only expired recruiter feedback and baseline observations; it never deletes workflow history or other observation types. Review-duration validity uses a separate 24-hour upper bound, not the feedback retention period. Baseline comparisons remain descriptive, show both sample sizes and periods, and do not establish causation or fairness.

## Data retention and deletion

Current behavior is not a comprehensive retention policy. Recruiter feedback and baseline observations have an enforced 90-day reporting/expiry period with owner-scoped lazy pruning on Impact API access. Resume analyses and skill evidence, workflow inputs/snapshots, and human-review records have no automatic expiry or deletion endpoint. Uploaded files and complete extracted resume text are not persisted. Session rows have expiry/revocation checks but no scheduled purge.

Recommended future policy, pending approval by the data controller: retain analysis/evidence and workflow/review records for up to 90 days; retain recruiter feedback and baselines for the existing 90 days; purge expired or revoked session rows after a documented operational grace period (recommended 30 days). Account deletion should delete only records owned by the authenticated account in one transaction, with reviewed foreign-key cascades covering sessions, analyses/skills, workflows/reviews and impact rows. These are recommendations only; no automatic cleanup, account deletion behavior, or schema change has been added. Do not treat this documentation as a legal retention determination.

## Deployment security requirements

The local launcher and Vite proxy are for development only. Deploy behind HTTPS, set exact HTTPS origins, keep `SKILLFAIR_AUTH_COOKIE_SECURE=true`, and use either same-origin API hosting or a separately reviewed credentialed-CORS policy. The API emits `X-Content-Type-Options`, frame, referrer, permissions, and API-response CSP headers. The React host must set its own document CSP and browser security headers. HSTS is emitted only when the ASGI request scheme is HTTPS; a TLS-terminating proxy that connects to the backend over HTTP must set HSTS itself. Forwarded headers are not trusted by the app. The reverse proxy/server must provide request-body read/idle timeouts, a request-body size cap, and edge rate limiting. In-memory body/rate controls do not coordinate across workers or instances.

## Dependency lock and vulnerability review

`requirements.txt` contains runtime dependency ranges only. `requirements-dev.txt` includes those runtime requirements plus test dependencies. `requirements-lock.txt` is the single pinned development/test environment, resolved and tested with CPython 3.14.7; it includes pytest 9.0.3 and AnyIO 4.15.1. To refresh it, create a clean CPython 3.14.7 virtual environment, install `requirements-dev.txt`, capture the resolved package pins with `python -m pip freeze` (excluding the environment's bootstrap tools), and review the full diff before replacing the lock. Then verify the pins with `python -m pip check` and rerun the backend suite. Regenerate and rerun tests for another interpreter/platform. The frontend uses `package-lock.json` and should be installed with `npm ci`. CI should run an approved scanner, for example `pip-audit --no-deps -r requirements-lock.txt`, and review findings before changing versions.

The focused security command runs authentication and API security cases. The next command runs database-independent backend tests while excluding the PostgreSQL integration module. The full default backend suite includes that module, which skips unless `SKILLFAIR_RUN_POSTGRES_INTEGRATION=1` is explicitly enabled. That opt-in test harness loads the ignored `.env.test.local`, validates the exact dedicated test database and runtime role, and verifies server identity before test records are created. CI explicitly sets `SKILLFAIR_RUN_POSTGRES_INTEGRATION=0`. It has no external PostgreSQL service or connection URL and performs no migrations; other tests may use isolated in-memory SQLite. Do not set the opt-in flag in CI or point integration tests at development, production, or Permission-Aware RAG databases. Integration tests are a separate, explicitly approved operation.

GitHub Actions is configured in `.github/workflows/ci.yml`. It uses Node.js 22 and CPython 3.14.7, installs the frontend with `npm ci` and backend dependencies from the pinned test lock, then runs frontend typecheck/lint/tests/build and backend syntax/import, focused security, and default test checks. CI sets PostgreSQL integration to `0`, has no external PostgreSQL service or connection URL, and performs no migrations or deployments; tests may use in-memory SQLite. Each job has a bounded runtime and pytest commands have individual timeouts. The workflow does not publish deployment artifacts.

Environment files, `.envrc`, `.npmrc`, secrets directories, local backup/database files, backend upload and package directories, and generated test artifacts are excluded from Vercel deployment uploads by the repository's `.vercelignore`. This is separate from `.gitignore`: Git exclusions affect what Git reports or stages, while `.vercelignore` controls files excluded from Vercel deployment packaging. The existing `backups/` directory is preserved. A `.vercelignore` file does not mean Vercel deployment is fully configured; no complete Vercel build, runtime, environment, or database deployment setup is claimed.

Minimum-sample suppression remains five eligible submissions/starts. `awaiting_data`, `insufficient_sample`, `measured`, and `unavailable` remain distinct; absent data is not shown as measured zero. Candidate feedback metrics are explicitly `unavailable`, not zero. The authenticated account association is not independent real-world identity verification. No resume text, evidence excerpts, comments, or individual records are included in measurement responses. These prototype metrics do not prove fairness, causation, candidate competence, or improved hiring outcomes. No actual pilot observations are available by default.

Use the existing `.env` in this directory if one is present; never replace it when updating configuration. If no `.env` exists, copy `.env.example` to create one. Start Uvicorn with `--env-file .env`; alternatively export the values in the shell. By default `SKILLFAIR_LLM_PROVIDER=none`: the frontend uses offline deterministic exact-term analysis and labels its evidence as mentions rather than proof of proficiency. An explicit AI request returns a controlled unavailable response instead of falling back to local mode.

To opt into Gemini analysis, set `SKILLFAIR_LLM_PROVIDER=gemini`, `SKILLFAIR_LLM_BASE_URL=https://generativelanguage.googleapis.com/v1beta`, `SKILLFAIR_LLM_API_KEY` to your private Google AI Studio key, and `SKILLFAIR_LLM_MODEL=gemini-3.8-flash` (or another supported model with structured-output support). The backend sends the key only in Google's `x-goog-api-key` header and calls the Gemini `generateContent` endpoint.

Alternatively, configure Groq by setting `SKILLFAIR_LLM_PROVIDER=groq`, `SKILLFAIR_GROQ_API_KEY` to a private Groq key, and optionally `SKILLFAIR_GROQ_MODEL` (defaults to `openai/gpt-oss-20b`). The backend sends requests to the fixed endpoint `https://api.groq.com/openai/v1/chat/completions` with Bearer authentication. `SKILLFAIR_GROQ_MAX_COMPLETION_TOKENS` sets the Chat Completions `max_completion_tokens` budget (default 8,192; accepted range 256–32,768). The default leaves room for a structured response while staying below the model's documented 65,536-token output cap; the effective total is also constrained by the model context window. The model ID is configurable; account access, model availability, quotas, and pricing depend on the Groq account and are not assumed. The implementation uses strict JSON Schema Structured Outputs for this initial model candidate, then validates the result with SkillFair's existing Pydantic schema and verbatim evidence checks. A response ending with `finish_reason=length`, missing content, or malformed/incomplete JSON is rejected; it is never accepted as a partial skills list. Do not commit `.env` or real candidate documents.

Gemini HTTP timeouts are independently configurable with `SKILLFAIR_GEMINI_CONNECT_TIMEOUT_SECONDS` (10 seconds by default) and `SKILLFAIR_GEMINI_RESPONSE_TIMEOUT_SECONDS` (120 seconds by default). Groq uses `SKILLFAIR_GROQ_CONNECT_TIMEOUT_SECONDS` and `SKILLFAIR_GROQ_RESPONSE_TIMEOUT_SECONDS` with the same defaults. All timeout values accept 1–300 seconds. A response timeout is the HTTP client's read-inactivity limit, not a total end-to-end request deadline. Logs distinguish connection and provider failures without logging API keys, request headers, resume contents, or raw provider messages. Gemini retries only a 503 `UNAVAILABLE` provider response, at most once. Groq requests are not automatically retried; timeouts, quota errors, and invalid requests are not retried.

The Skills Discovery upload accepts multipart `analysis_mode` (`local` or `ai`) and consent fields. New clients send `consent_to_ai_provider` (`true` or `false`) together with `consented_ai_provider` (`gemini` or `groq`); the backend requires the named provider to match its current configuration. The legacy `consent_to_gemini` remains supported for Gemini clients only. The frontend defaults to `local` and calls `GET /api/skills/provider` to display the configured provider and whether its settings are present. This safe status endpoint never exposes credentials and does not verify account access. Selecting `ai` requires fresh consent for that provider and request; the backend enforces it before extracting resume text and before any provider request. Local mode skips provider configuration and never calls an external provider. Missing settings return a controlled error; the application never silently changes providers or falls back to local analysis. Consent is not retained. The disclosure names the recipient and explains that SkillFair cannot control provider-side retention or handling. Consent does not guarantee deletion or any specific provider retention behavior.
